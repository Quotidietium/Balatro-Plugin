# 开发规范（Balatro-Plugin）

> 本文件记录"怎么做"的约定与决策。标注 `[待决策]` 的条目需用户确认后定稿（见末尾"待决策清单"）。

## 1. 平台与依赖（已定）

- 目标：**Minecraft 1.21.11**，`api-version: 1.21.11`，运行于 **Papo**（Paper 1.21.11 fork）。
- 编译依赖：`io.papermc.paper:paper-api:1.21.11-R0.1-SNAPSHOT`（`compileOnly`/`provided`，服务端已提供）。
- Java：**JDK 21**（`--release 21`，与 Papo 工具链一致）。
- 视为普通 Paper 1.21.11 插件开发；不依赖任何 `papo.*` 包（不存在）。

## 2. 构建系统 `[待决策]`

- 候选 A：**Gradle Kotlin DSL** — 与 Papo 服务端一致，现代 Paper 插件主流，易配 toolchains/影子 jar。
- 候选 B：**Maven** — 与 doudizhu 参考一致，简单直接。
- （二选一，见末尾决策；建议 A，与服务端及 note 体系一致。）

## 3. 包名与坐标 `[待决策]`

- 候选 `groupId`（如 `com.zurker.balatro` 或自定义），`artifactId=balatro`（或 `Balatro`）。
- 包根建议：`com.<you>.balatro`，子包沿用分层（见 §5）。

## 4. 版本与发布（已定）

- 语义化版本，从 **0.1.0** 起；`plugin.yml`/`paper-plugin.yml` 的 `version` 与之一致。
- 每个发版写 `note/release/<版本号>.md`（基线 / 改动 / 兼容性 / 验证）。
- 性能测试报告放 `note/report/perf/`，文件名带日期与主题。

## 5. 代码分层（沿用 doudizhu 范式 + balatro 引擎移植）

```
com.<you>.balatro
├── BalatroPlugin            主类：装配、注册命令/监听、生命周期
├── engine/                  ← balatro 引擎移植（纯逻辑，无 MC 依赖）
│   ├── Rng.java                (rng.js)  种子哈希 + mulberry32 + 命名流
│   ├── Data.java               (data.js) 静态数据表（牌型/牌组/Boss/塔罗…）
│   ├── Card/HandType/Suit/...  游戏模型（Card 含唯一 id + 增强/版本/蜡封）
│   ├── Joker.java + 钩子接口    (jokers.js) 小丑注册表与钩子
│   └── Engine.java             (engine.js) 状态机/计分/商店/补充包/胜负
├── session/                 会话管理：每玩家 RunState（Map<UUID,...>）、加载/存档
├── render/                  渲染层 [待决策：全息 TextDisplay 或 GUI Inventory]
├── listener/                交互监听（射线 或 InventoryClickEvent）
├── command/                 命令（执行器 + Tab 补全）
├── config/                  配置包装 + 热补齐（借鉴 ConfigCompleter）
└── integration/             经济/PlaceholderAPI 等可选集成
```

### 移植正确性红线（来自 balatro）

- `rng/data/engine/jokers` 四个纯逻辑模块**逐方法翻译**；`game.js`（DOM）丢弃，MC 端重写渲染。
- **必须保持各 `stream(name)` 调用顺序与原版一致**，否则种子不复现（这是移植正确性的核心约束）。
- 引擎层**零 MC 依赖**（纯 POJO），便于单测与后续替换渲染层。

## 6. 渲染与交互 `[待决策]`

- 候选 A：**世界全息渲染**（TextDisplay/ItemDisplay + Matrix4f + 射线交互）— 沿用 doudizhu，沉浸感强，围观友好；
  但 Balatro 面板多（小丑/消耗品/手牌/出牌区/商店/补充包），实体与射线复杂度高。
- 候选 B：**箱子 GUI**（Inventory + ItemStack，`InventoryClickEvent`）— 交互稳、开发快、MC 玩家熟悉；
  视觉上不如原版"卡牌"。
- 候选 C：**混合**（GUI 为主 + 关键处全息点缀）。
- （三选一，见末尾决策。）

## 7. 会话模型 `[待决策]`

- 候选 A：**每人独立单局**（Balatro 本质单人 Roguelike）— `Map<UUID, RunState>`，互不干扰，最贴近原作。
- 候选 B：**多人围桌**（社交化，借鉴 doudizhu 多桌）— 需自定义多人规则，偏离原作。
- （二选一，见末尾决策；建议 A。）

## 8. MVP 范围 `[待决策]`

Balatro 内容量极大（150+ 小丑、28 Boss、塔罗/星球/幻灵/标签/优惠券…）。建议分阶段：
- **0.1.0 核心**：标准 52 张牌、基础计分（chips×mult）、13 牌型判定、若干基础小丑、small/big/boss 盲注与目标分、回合/出牌/弃牌/抽牌、通关 8 底注。暂不含商店/补充包/塔罗星球/挑战。
- **0.2.0 经济与构筑**：商店（小丑/卡牌/补充包/优惠券/重掷）、塔罗/星球消耗品、增强/版本/蜡封、标签。
- **0.3.0 深化**：全部 Boss、幻灵牌、挑战模式、种子复现与分享、配置化。
- （范围以用户确认为准。）

## 9. Git 与提交规范（已定，遵照全局 CLAUDE.md）

- 细粒度提交：每个独立改动一个 commit，便于回滚。
- **不写 co-author / 协作者**（除非用户显式允许）。
- 必要时建分支，避免直接改坏 `main`。
- 提交信息用简洁祈使句（中文或英文均可，与上下文一致）。

## 10. 编码规范（建议）

- 引擎层纯逻辑、可单测；MC 相关（Bukkit API）只进 render/listener/command/session。
- 卡牌、小丑等一律**唯一 id**标识，状态可变（增强/版本/蜡封/extra）。
- 随机一律走 `Rng` 命名流，禁止裸 `Math.random()`/`new Random()`，保证种子复现。
- 文本用 Adventure `Component`（非旧式颜色码）。
- 配置借鉴 doudizhu：缺失才释放默认 + 热补齐新字段 + `reload()` 支持。
