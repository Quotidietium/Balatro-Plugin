# 开发规范（Balatro-Plugin）

> 本文件记录"怎么做"的约定与决策。关键架构选择已与用户确认（见 §0）。

## 0. 已确认的关键决策

| 项 | 决策 | 备注 |
|---|---|---|
| 渲染方式 | **世界全息渲染** | 沿用 doudizhu：TextDisplay/ItemDisplay 实体 + Matrix4f 定位 + 射线交互；不用箱子 GUI |
| 构建系统 | **Gradle Kotlin DSL** | 与 Papo 服务端、note 体系一致 |
| 会话模型 | **每人独立单局** | `Map<UUID, RunState>`，每玩家各打各的种子局，互不干扰 |
| 范围目标 | **实现完整功能** | 项目终极目标 = 完整 Balatro（150+小丑/28Boss/塔罗/星球/幻灵/优惠券/标签/增强版本蜡封/补充包/挑战/种子复现），按版本路线图渐进达成（见 §8） |

> 范围口径：用户选"实现完整功能"。理解为**项目终极目标**，分版本累积达成；
> 若要求 0.1.0 一次性全量，需用户另行确认。

## 5. 代码分层（沿用 doudizhu 范式 + balatro 引擎移植）

```
com.zurker.balatro
├── BalatroPlugin            主类：装配、注册命令/监听、生命周期
├── engine/                  ← balatro 引擎移植（纯逻辑，零 MC 依赖，可单测）
│   ├── Rng.java                (rng.js)  种子哈希(FNV-1a)+mulberry32+命名流
│   ├── Data.java               (data.js) 静态数据表（牌型/牌组/Boss/塔罗…）
│   ├── model/                  Card(唯一id+增强/版本/蜡封)/Suit/Rank/HandType/...
│   ├── Joker.java + 钩子接口    (jokers.js) 小丑注册表与钩子(onScore/onScoreCard/onHeld/onPlayHand/onDiscard/onEndRound/onShop)
│   └── Engine.java             (engine.js) 状态机(blindSelect/round/shop/pack/end)/计分/商店/补充包/胜负
├── session/                 会话：Map<UUID,RunState> + 存档 + PlayerQuit清理
├── render/                  全息渲染（TextDisplay/ItemDisplay + Matrix4f 布局 + 视图切换）
├── listener/                射线交互（手牌/按钮/商品/小丑）+ 节流
├── command/                 命令（执行器 + Tab 补全）
├── config/                  配置包装 + 热补齐（借鉴 ConfigCompleter）+ 布局 yml
└── integration/             经济(Vault)/PlaceholderAPI/资源包(CraftEngine/ItemsAdder，可选)
```

### 移植正确性红线（来自 balatro）

- `rng/data/engine/jokers` 四个纯逻辑模块**逐方法翻译**；`game.js`（DOM 渲染）丢弃，MC 端重写渲染。
- **必须保持各 `stream(name)` 调用顺序与原版一致**，否则种子不复现（移植正确性核心约束）。
- 引擎层**零 MC 依赖**（纯 POJO + JUnit 单测），渲染层只读引擎状态、回写玩家操作。

## 6. 渲染与交互（已定：世界全息）

借鉴 doudizhu 的 TextDisplay 全息方案，针对 Balatro 复杂面板的设计要点：

- **视图即一组实体**：盲注选择/回合/商店/补充包/结算各对应一组全息实体；切换视图 = despawn 旧组 + spawn 新组（或复用实体改变换/文本）。
- **面板布局配置化**：每个区域（小丑区/消耗品区/出牌区/手牌/按钮/商店行）的锚点、间距、缩放写入 yml（借鉴 doudizhu 的 first/second/third 多 yml 布局），便于调位且不重编译。
- **卡牌视觉分层**：
  - 基础牌面用 TextDisplay（花色符号♠♥♣♦ + 点数 + 颜色）即可起步，零资源包依赖；
  - 增强/版本/蜡封用文字标签或额外小实体标注；
  - 后续可升级为 ItemDisplay + 自定义贴图（资源包 `CustomModelData`，或接 CraftEngine/ItemsAdder——doudizhu 已 softdepend 这两者，并提供 `CardSkinManager` 可参考）。
- **交互**：右键 `PlayerInteractEvent` + 射线检测各区域（`raycastHand`/`raycastButton`/`raycastShop`/`raycastJoker`），命中即选中/购买/使用/出售/重排序；每玩家 120ms 节流；动作配 `UI_BUTTON_CLICK` 音效。
- **私有可见**（契合"每人独立单局"）：每玩家的牌桌实体 `setVisibleByDefault(false)` + `showEntity(plugin,e)` 仅本人可见；玩家可在自己牌桌前围观他人不可见。
- **生命周期**：`setPersistent(false)` + scoreboard tag 追踪；`onEnable` 清残留、`onDisable` `shutdownAll`、`PlayerQuit` 收牌桌。
- **性能**：控制同时存在实体数、合理 `setViewRange`、视图切换及时 despawn；状态变更只重渲染变化部分（差量更新）。

## 7. 会话模型（已定：每人独立单局）

- 玩家通过命令（如 `/balatro play`）在自己附近生成/进入**专属牌桌**，开始一局种子局。
- `SessionManager` 持 `Map<UUID, RunState>`；`RunState` 包装引擎状态 + 该局的渲染实体句柄。
- **退出即弃，不存档**：玩家退出命令 / `PlayerQuitEvent` / 放弃按钮 → 销毁 `RunState` + despawn 实体，不落盘、不续局。
- 互不干扰：A 的操作不触碰 B 的牌桌（私有可见 + 按玩家分发）。

## 7.1 预留扩展 API（已定：接口先行，详见 [项目计划书.md](项目计划书.md) §7）

为后期"得分排名 / 过关奖励 / 统计 / 经济联动 / 第三方扩展"预留稳定扩展面，**不改引擎与渲染**：

- **自定义事件**（`api/event/`，Bukkit Event，关键节点可取消）：
  `BalatroRunStartEvent`(可取消) / `BalatroHandScoreEvent` / `BalatroBlindResultEvent` /
  `BalatroAnteClearEvent`(过关奖励挂钩) / `BalatroRunEndEvent`(排名入库)。
  引擎层经纯逻辑 `EngineListener` 上报，`EngineEventBridge` 在主线程翻译为 Bukkit 事件。
- **服务接口**（`api/service/`，接口 + 默认实现，可替换）：
  `EconomyService` / `RewardService` / `StatsService` / `LeaderboardProvider` / `PlaceholderProvider`，
  默认实现兜底（无经济/内存统计），后期接 Vault/PlaceholderAPI、持久化排名、可配置奖励。
- **设计原则**：引擎只发事件、不感知服务；接口稳定在 `api/`；默认实现可被配置或其他插件替换。

## 10. 编码规范（建议）

- 引擎层纯逻辑、可单测；MC 相关（Bukkit API）只进 render/listener/command/session/integration。
- 卡牌、小丑等一律**唯一 id**标识，状态可变（增强/版本/蜡封/extra）。
- 随机一律走 `Rng` 命名流，禁止裸 `Math.random()`/`new Random()`，保证种子复现。
- 文本用 Adventure `Component`（非旧式颜色码）。
- 配置借鉴 doudizhu：缺失才释放默认 + 热补齐新字段 + `reload()` 支持。
- 实体/状态变更走主线程（Bukkit API 非线程安全）；耗时计算（如有）放异步再回主线程渲染。
