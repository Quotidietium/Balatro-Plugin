# Balatro v0.4.47 — P9 性能优化：商店生成层

> 基线：Minecraft 1.21.11 / Paper API（Papo 服务端）。性能战役第二期第 2 轮（P9）。

## 改动（Shop.java，行为零变化）

1. **小丑稀有度池静态分桶**：`JOKERS_BY_RARITY`（4 桶，桶内保持原版 ORDERED 序）——
   原每次生成商品全量遍历 150 小丑逐个 `rarityOf(key)` 字符串哈希查找；现直接迭代
   目标稀有度桶。池按桶大小精确预置（单次分配）。
2. **塔罗/幻灵/包池共享静态化**：无禁入（标准局常态）时塔罗池即 `Data.TAROTS`、
   幻灵商店池/商店包池用静态共享列表（内容/顺序与原地筛选逐元素一致）；有禁入才现筛。
3. **权重表零分配**：商品类型权重从 `List<int[]>`+每次 4~5 个 `int[]` 装箱改为平置
   int 数组内联加权抽取——与 `Rng.Stream.weighted` 的算术**逐位一致**（同序累加/恰一次
   next()/按序减重），仅去装箱与 lambda 分发。
4. 列表精确预置：ShopData 卡位 4/包 2/券 2、商品列表 shopSlots、券可用池 32。

## 基准（best-of-3 交替顺序交错 A/B，vs v0.4.46）

| scenario | 时间 | 分配 B/op |
|---|---|---|
| shopGen | **3.430×**（12,501→3,645 ns/op） | 11,873 → **8,023（−32.4%）** |
| playHand | **1.602×**（8,630→5,386 ns/op） | 11,550 → **10,150（−12.1%）** |
| fullRun | **1.189×**（935,061→786,432 ns/op） | 2.0M → 1.992M（−0.4%） |

playHand 场景每 ~5 op 胜出回合开一次商店，商店生成的 CPU 大头（每次开店 ~900 次
rarityOf 字符串哈希查找）被分桶消灭后大幅继承；fullRun 每局 ~24 次开店，省 ~100μs/局。
三对两方向结果一致；9 场景 sinkΔ 逐位一致（458 测试全过）。
详见 [report/perf/2026-08-16-P9-商店生成层.md](../report/perf/2026-08-16-P9-商店生成层.md)。

公开签名零变化；随机流消耗次序不变（加权抽取逐位等价论证见报告）。0.4.x 直接替换 jar。
