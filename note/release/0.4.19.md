# Balatro v0.4.19 — 服务注册表三向替换一致性修复

> 基线：Minecraft 1.21.11 / Paper API（Papo 服务端）。本轮深审服务持久化层（文件 I/O、排行榜聚合、
> 服务装配），修复一处运行期服务替换的静默不一致缺陷。**结论：文件持久化原子写/容错/有界全部正确**。

## 修复

### setLeaderboard 未同步注入当前 stats / winCounter（静默不一致）

**现象**：第三方插件在 `onEnable` **之后**调用 `services.setLeaderboard(...)` 换入一个新的
`MemoryLeaderboard` 时，新排行榜：
- 仍持有其**构造时**的旧 `StatsService`（新记录不再反映到排名）；
- `winCounter` 恒为 null → `topAggregated` 的 `winCount` **恒为 0**。

这正是 `setStats` 注释里要防的「静默不一致」，但 `setLeaderboard` 自身漏了同样的同步处理。

**当前默认装配为何没暴露**：onEnable 顺序是 setStats → setLeaderboard → setWinCounter，
`setWinCounter` 在最后、会注入最终的 ml——**碰巧正确，但依赖调用顺序**，属脆弱不变性。

**修复**：`setLeaderboard` 与 `setStats`/`setWinCounter` 对齐——替换排行榜时把当前 stats 与
winCounter 一并注入。三向（stats / winCounter / leaderboard）任一替换都保持同步，不再依赖顺序。

**新增回归测试** `setLeaderboardRebindsCurrentStatsAndWinCounter`：配齐 stats+winCounter 后换入
全新 MemoryLeaderboard（构造时给的是别的源），断言替换后读到当前 stats（bestAnte）与 winCounter
（winCount）。

## 持久化层确认（无缺陷，留档）

逐行核查 `FileStats` / `FileWinCounter` / `MemoryLeaderboard` / `Services`：

- **FileStats**：内存 + 文件均以 `MAX_RECORDS=10000` 有界（只留最近，排行语义即最近最佳）；
  加载用流式 + 尾部环形缓冲（启动内存无尖峰）；超限一次性压缩重写；compact 用**原子写**
  （先写 .tmp 再 move，防中途崩溃丢历史）；decode 严格 7 段 + 种子长度/控制字符校验（脏行丢弃）。
  软失败语义已注释声明（持久化失败不影响局内，排行榜非关键数据）——可接受设计取舍，非缺陷。
- **FileWinCounter**：整文件重写 + 原子写（`moveAtomic`，ATOMIC_MOVE 不支持时降级普通覆盖）；
  计数远小于统计记录（仅通关局），无需压缩；load 容错（脏行跳过）。
- **MemoryLeaderboard**：排序 comparator 用 `thenComparing(子comparator)` 而非链式 `.reversed()`
  ——避免第二个 reversed 反转整个比较器（含前段）导致 won 变升序。注释已明确此陷阱，实现正确。
- **并发**：`record`/`all`/`increment`/`count` 均 `synchronized`，HashMap/ArrayList 由锁保护；
  `load` 仅构造期调用（无并发）。
