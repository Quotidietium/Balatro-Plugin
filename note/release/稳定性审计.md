# 稳定性与安全审计记录

> 目标：确保长时间高负载、多用户高频使用下的稳定性；客户端输入一律不可信（可篡改客户端
> 伪造任意数据包/实体 id）。与 [逻辑审计.md](逻辑审计.md)（玩法逻辑对照原版 JS）互补，
> 本文件聚焦**数据操作、资源生命周期、输入校验、并发与长期运行**类问题。
>
> 每轮审计覆盖不同方面；已修项标注提交，待办项标注后续轮次。

## 审计轮次

### 轮次 1（2026-08-11）— 输入校验 / 会话层 / 持久化

**覆盖面**：命令层（BalatroCommand）、会话层（GameSession/SessionManager/SessionListener）、
全息交互面（BoardListener/RoundBoard）、实体生成（Holo）、统计持久化（FileStats）。

**已逐项核验、确认无问题（0.3.6 已加固）**：

- 全息交互归属：`RoundBoard.ownsInteraction` 用本牌桌的 `interactions` 列表校验，篡改客户端
  无法命中他人牌桌或来路不明的 `balatro_i_*` 实体；`dispatch` 外包 try/catch 防异常逃逸。
- 宽松解析：`parseIntSafe` 对越界/空/非数字一律返回 null，绝不抛出。
- 选中态防伪：`toggleSelect` 拒绝不在手牌中的 id；`update` 剪除陈旧选中 id；手牌变更后必清空选中
  → `selected` 在出牌时必为手牌子集，无 TOCTOU（同主线程原子操作）。
- 索引约定一致：全息 tag 用 0-based（`shop:i`/`pick:i`/`joker:i`/`cons:i`），`parseIntSafe` 原样透传；
  命令层 1-based（`parseOne` 减 1）→ 引擎 0-based。无 off-by-one。
- 引擎边界自检：`Consumables.use` 等对 idx 做 `<0||>=size` 校验，故 `cmdUse` 未单独 `<0` 拦截
  亦不会越界（仅报错文案略逊，非崩溃）。
- 实体非持久：`Holo.text`/`Holo.interaction` 均 `setPersistent(false)` + `balatro_board` 标签；
  崩溃后重启不残留（不入盘）。插件 `onDisable→shutdownAll` 逐一 despawn；`PlayerQuit` 回收。
- 并发：游戏状态变更全在主线程（命令/事件），`FileStats` 方法级 `synchronized`，无数据竞争。

**已修复**：

| # | 位置 | 问题 | 修正 | 提交 |
|---|---|---|---|---|
| 1 | `FileStats.load` | `readAllLines` 把整个文件读入内存；文件只在启动加载时压缩，长时高负载不重启可膨胀至数十万行，下次启动造成内存尖峰与变慢 | 改流式读取，内存仅留最近 MAX_RECORDS 条 | `3f2208f` |
| 2 | `FileStats.record` | 文件端长期运行只增不减（压缩只在 load 触发），数周不重启文件无限膨胀 | 每累计 MAX_RECORDS 次追加触发一次 `compact` 收敛回 ≤MAX | `3f2208f` |
| 3 | `FileStats.record` | 每次 record 都 `createDirectories`（stat 父目录），高频写入无谓开销 | 改 `dirEnsured` 仅首次执行一次 | `3f2208f` |

回归：新增 `FileStatsTest`（往返 / 超大文件流式有界+压缩 / 脏行丢弃 / 父目录自动创建），4 例全过（`64ee157`）。

**评估后判定可接受（不改）**：

- `FileStats.record` 每次开/关一次 BufferedWriter 做追加：单局 Balatro 耗时数分钟，game-end
  频率仅每秒数次，主线程单次追加以微秒计，不构成 TPS 风险；引入异步写线程的复杂度/生命周期风险
  不划算。若未来出现极端负载再评估。

**待办（后续轮次）**：

- 排行榜样例语义：通关 ante8 后进无尽、于无尽死亡会再记一条「失败 底注9+」，与「通关 底注8」
  并存。排序虽 won 优先，但是否应记录无尽死亡属产品决策（待确认），暂不改动。
- 待覆盖方面：BoardMoveListener（跨世界迁移健壮性）、Engine 内部边界（Shop/Packs/RunState.sell*
  等引擎入口的防御性 bounds）、MemoryLeaderboard/MemoryStats、命令层小瑕疵（cmdUse `<0` 文案）、
  命令异常路径整体兜底（命令执行器层面是否需统一 try/catch）。

### 轮次 2（2026-08-11）— 引擎入口 / 状态机 / 经济 / 渲染迁移

**覆盖面**：引擎入口边界（Shop/Packs/RunState sell*/gain*）、随机流缓存（StreamSource）、
回合结束经济（interest/rental/perishable）、状态机推进（nextRound/continueEndless/selectBlind）、
出牌/弃牌校验（playHand/discard）、跨世界迁移（BoardMoveListener）、静默桩扫描、抽样小丑
（todo/cavendish/square）。对照 REF 原版 engine.js/jokers.js 逐行确认。

**结论：本层全部核验通过，无逻辑错误。**

- 引擎入口均自检边界：`Shop.buyCard`/`buyPack`/`Packs.pick`/`RunState.sellJoker`/`sellConsumable`/
  `addConsumableKey`/`gainJoker`/`Consumables.use` 全部 `idx<0||>=size` 拦截；`playHand`/`discard`
  全程校验（phase/次数/1-5 张/去重/`findInHand` 非空）→ 构造 cardIds 亦被优雅拒绝，不抛异常。
- `StreamSource.stream` 用 `computeIfAbsent` 按名缓存、状态连续推进 → 种子复现红线完好。
- 「信用卡」joker 设 `credit=20`（对照 REF，即真版 Credit Card 券），money 可至 −$20 属**设计**；
  利息有 `money>0` 守卫 + `interest>0` 双保险，负余额不产生负利息（与 REF engine.js 1062-1065 逐字一致）。
- `endRound`（Java 820-896）是 REF engine.js（1045-1118）的**逐行忠实移植**：奖励/剩余出牌/利息/
  黄金牌/蓝蜡封/`onRoundEnd` 快照/租赁 `money-=3`（无 clamp，同原版）/易腐/`money+=gain`/投资标签全一致。
- 易腐 `perishCount=5` 在 `JokerInstance` 构造时初始化（等价 REF 的 `null→5` 默认），5 回合失效正确。
- 状态机：`nextRound` 通关 ante8 → END + `endlessPending`；`continueEndless` 重置 `won=false`
  → **无尽模式死亡不会重复触发 finishRun(true)**（轮次 1 的待办经核实已正确处理）。
- `BoardMoveListener`：`isCancelled`/空世界守卫/跨世界先短路再 `distanceSquared`/延迟 1 tick
  +`isOnline` 复查/`relocate` 外 try-catch，迁移健壮。
- 静默桩扫描：无 TODO/桩方法。`Consumables` 的「未实现」为 switch 默认分支（22 塔罗+18 幻灵全实现，
  故不可达）；`TODO_JOKER` 是真 joker「待办清单」，`onPlayHand`/`onRoundEnd` 钩子完整。
- 抽样小丑 todo/cavendish/square 对照 REF jokers.js 逐行一致（todo 首回合默认 pair 同原版）。

**已修复（命令层边界一致性）**：

### 轮次 3（2026-08-11）— 牌型判定边界（四指同花顺/皇家）+ 排行榜/统计服务

**覆盖面**：`HandEval`（同花顺/皇家/四指/石头牌/万能牌边界）、`MemoryLeaderboard`、`MemoryStats`。
按用户指示，REF 与真版冲突处以**联网核实**为准（REF 不一定正确）。

**已逐项核验、确认无问题**：

- `MemoryLeaderboard`：`top(n)` 有 `n<=0` 守卫 + 防御性拷贝；比较器 won→ante→时间 正确。
  `bestOf` 按 RANK 选最佳。基于 `StatsService.all()`（FileStats 已有界，见轮次1）。
- `MemoryStats`：`Collections.synchronizedList` + `all()` 在 `synchronized(records)` 内拷贝，线程安全。
  **但无界**（永不裁剪）——生产环境 `BalatroPlugin` 始终用有界的 `FileStats`，故 `MemoryStats` 为
  非生产路径的潜在隐患（若被替换接入需自行有界化），暂记不修。

**已修复（联网核实的逻辑缺陷）**：

| # | 位置 | 问题 | 修正 | 提交 |
|---|---|---|---|---|
| 5 | `HandEval` 同花顺/皇家计分 | 四指(Four Fingers)下打「4 同花 + 1 异花」凑出的同花顺/皇家，计分用 `addAll(suited)`，**把异花的第 5 张牌也算进计分牌**（虚高分） | 同花顺/皇家改在同花牌集(`flushCards`)内重判顺子；计分牌仅取同花色牌（异花牌不计分） | (本轮) |
| 6 | `HandEval` 皇家判定 | 原判 `rs.contains(10)&&rs.contains(14)`（要求含 A），但四指下 K-Q-J-10 同花也是皇家（无 A） | 改「同花顺窗口内所有点数 ≥10」即皇家（含四指 K-Q-J-10 / A-K-Q-J） | (本轮) |

**联网核实要点**（REF 此处与真版冲突，以真版为准）：
- 真版四指：顺子/同花/同花顺/皇家均降至 **4 张**；皇家 = 「全 ≥10 的同花顺」，K-Q-J-10 或 A-K-Q-J 同花即皇家。
  来源：[Four Fingers](https://balatrogame.fandom.com/wiki/Four_Fingers) / [Poker Hands](https://balatrogame.fandom.com/wiki/Poker_Hands) / [Steam 讨论](https://steamcommunity.com/app/2379780/discussions/0/715609860235874869/)。
- 本次修正**仅改计分牌**（异花牌不再计入同花顺/皇家计分）；**牌型判定对非四指完全不变**
  （非四指同花时 `flushCards==suited`），`EvalGoldenTest`(eval.txt 15 例) 全过无回归。
- 过程纠偏：初判以为「异花 A 凑 broadway → 误判 ROYAL 牌型」，联网后确认 10JQK 同花本就是
  K-Q-J-10 皇家（牌型正确），真正错误只在计分（异花 A 不应计分）。已按真版修正。

回归：`FourFingersTest` 增至 7 例（皇家/同花顺 异花牌不计分 + 非四指皇家回归），全过。

**待办（后续轮次）**：`Data` 表项数值抽查；高并发实体开销实测；石头牌/万能牌在更多牌型中的计分抽样；
无尽死亡记「失败」条目（待产品决策）。
