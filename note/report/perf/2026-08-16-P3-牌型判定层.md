# P3 性能优化报告 — 牌型判定层（HandEval）

> 日期：2026-08-16 · 分支：`perf/plugin-performance` · 版本：v0.4.40 → **v0.4.41**
> 基线：P1 提交（优化前引擎）· 测量协议：best-of-3 交错 A/B

## 优化点

`HandEval.evaluate` **算法重写**（行为逐字保持）：原实现每次判定分配
`TreeSet`/`LinkedHashMap`+每组 `ArrayList`/Stream 管线（`.stream().map(List::size).toList()`、
`.mapToInt().toArray()`）/`HashSet`，基准实测 ~1.3KB/次。该路径是全息牌桌
「实时牌型评估」热路径（每次选牌变化都触发），也是任何手牌枚举型策略的瓶颈。

改为平坦数组：

| 原结构 | 新结构 |
|---|---|
| `LinkedHashMap<Integer,List<Card>> byRank` + 每组 ArrayList | `int[15] cnt` 点数计数（组内顺序=手牌原序，遍历 `suited[]` 即还原） |
| `counts` List + Stream + sort | 循环求前两大计数 c0/c1 |
| `TreeSet<Integer>` 去重升序 + Stream toArray | `boolean[15] present` + 计数展开为升序 `int[]` |
| `HashSet<HandType> contains` | `EnumSet`（单 long 位图） |
| `List<Card> suited/flushCards` | `Card[n]` 数组 + 按需循环 |

**语义对齐论证**：
- 分支判定次序、`need`/`straightLen` 口径、Four Fingers/Shortcut/Smeared/Splash 行为原样保留；
- 计分牌选择：组间点数降序（原 `rankKeys.sort(reverseOrder())` ⇔ 新 `rk=14..2` 循环）、
  组内手牌原序（原 LinkedHashMap 插入序 ⇔ 新 suited 数组序）；顺子/同花/同花顺/石头/水花
  分支逐字保留；
- 数组边界安全：非石头牌 rank 恒 ∈[2,14]（力量 `<14` 才 +1、死亡复制合法 rank、牌组构建
  均 2..14；rank 0/-1 仅存在于 enh=STONE 的壳，进不了 suited）。
- 输出 `Result(type, scoring, contains)` 契约不变（第三方只读该类）。

**红线核对**：判定不消耗随机流，无种子复现影响；458 测试全过
（Eval/FourFingers/HandEvalEdgeCase/HandEvalChaos + 全部黄金锁定）。

> playHand/shopGen/discard 的负 delta 均在未触碰路径的噪声带内（本协议下 ±10%）。
> fullRun 分配暴降 5× 的原因：自动驾驶策略每手枚举 ~255 个子集逐一判定，
> evaluate 的分配削减被放大到整局尺度。

## 结论

牌型判定从「集合框架 churn」重写为「平坦数组扫描」：**3.66× 提速、6.5× 分配削减**，
并传导到整局吞吐（2.24×，累计）。下一轮 P4 聚焦 playHand 计分管线本身
（15.6KB/op 分配：多重 jokers 快照、`List.of(values())` 重建、`Objects.hash` 装箱等）。
