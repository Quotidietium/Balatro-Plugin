# P8 — 构局路径分配削减（v0.4.46）

> 日期：2026-08-16 · 分支 `perf/plugin-performance`（延续 P1–P7 战役的第二期）
> 基线：v0.4.45（b64eca6）worktree 交错 A/B · 红线：行为零变化（458 测试 + sinkΔ）

## 一、热点定位（数据驱动：JFR jdk.ObjectAllocationSample）

对 playHand 场景做 JFR 分配采样（settings=profile，主线程聚合，按「首个引擎帧」归因），
总计 ~3.0GB 采样分配中：

| 来源 | 占比 | 归因 |
|---|---:|---|
| ArrayList.grow 扩容链（Arrays.copyOf） | ~26% | fullDeck 10→…→49 五级扩容、drawPile/discardPile 首回合逐级扩容、商店池列表 |
| Card ×52（buildFullDeck/makeCard） | ~17% | 构局必要状态（每次 reset 摊销 ~10 张/op），不可池化（红线） |
| RunState/Mods 字段初始化 | ~12% | HashMap/HashSet 壳 + 列表壳（Mods 的禁入集合为 public final，API 红线不可惰性化） |
| 字符串拼接（msg/事件文案） | ~12% | 功能性输出，保留 |
| Shop.genShop/makeJokerItem | ~6% | → P9 轮处理 |
| computeFlags new HashMap（gainJoker×5/回合 高频重算） | ~2% | 每次重算丢弃旧表 |
| 其余（HandEval 数组/Stream 壳/迭代器等） | ~25% | P3–P6 已覆盖或小项 |

**结论**：playHand 场景的每 op 分配大头并非计分管线本身，而是 **每 ~4-5 op 一次 reset
所摊销的构局成本**——构局路径优化对 playHand/discard/shopGen/createRun 全部生效。

## 二、改动（4 处，均行为零变化）

1. `RunState.fullDeck = new ArrayList<>(52)`：标准/绝大多数挑战牌组恰 52 张，单次精确
   分配替代五级扩容链。
2. `startRound`：`drawPile.clear()` 后 `instanceof ArrayList → ensureCapacity(fullDeck.size())`，
   首回合一步到位（第二回合起 P5 已复用容量）；`discardPile` 同理。字段声明保持 `List`，
   第三方替换非 ArrayList 实现时自动跳过（仅失优化）。
3. `computeFlags` 双缓冲：`RunState.flagsSpare`（包内协作字段）停驻旧表，备用表 clear+重填。
   **语义论证**：旧表停驻时内容冻结，与原「换新表、旧表留给持有者」一致；全部读取方
   （isFace/isSuit/HandEval/prob/startRound 局部 f——均在钩子前使用完毕）都是现取现用，
   无跨重算持快照者。稳态每局仅 2 张 HashMap。
4. `chooseBoss` 池静态化：`BOSS_POOL_REGULAR`(23)/`BOSS_POOL_FINISHERS`(5) 共享不可变，
   内容仅取决于 `ante % 8 == 0`，`st.pick` 只读；随机流消耗次序不变。

## 三、测量（best-of-3 交错 A/B）

| scenario | 基线 ns/op | 终版 ns/op | 加速比 | 分配 B/op（基线→终版） |
|---|---:|---:|---:|---|
| createRun | 1,155 | 1,044 | **1.106×** | 5,806 → **4,726**（−18.6%） |
| shopGen | 16,568 | 14,102 | 1.175× | 12,953 → **11,873**（−8.3%） |
| discard | 480 | 450 | 1.067× | 557 → **477**（−14.4%） |
| playHand | 10,430 | ~8,760† | ~1.02-1.03×† | 12,670 → **11,518**（−9.1%） |
| handEval | 92 | 92 | 1.000× | 231 → 231 |
| roundCycle | 146,747 | 157,351 | 噪声带‡ | 229,380 → 228,426（−0.4%） |
| fullRun | 1,059,723 | ~1,063,000† | 噪声带‡ | 1,996,673 → 1,995,070（−0.1%） |
| streamLookup / rngNext | 2 / 1 | 2 / 1 | 1.000× | 0（未触及） |

† playHand/fullRun 的时间在 3 对套件内受顺序偏置与漂移干扰（每对固定先基线后终版，
   后跑者系统性承压；fullRun 单次中位数波动实测 ±25%）。以**交替顺序**（cur→bl、bl→cur）
   复测：playHand 两个方向均快 2–3%；fullRun 两方向一快一慢，判噪声带。
‡ roundCycle 分配 −0.4% 与 fullRun −0.1% 符合预期：构局在其总量中占比极小
   （roundCycle 每 ~40 op 一次构局、fullRun 每局 ~2.0MB 对构局 ~6KB）。

**方法学更新**：交错配对内也要交替先后顺序（bl,cur / cur,bl），消除「配对内后跑者
系统性承压」的偏置；时间结论存疑时以交替方向复测为准。分配字节/op 逐对完全稳定
（同版本三次运行逐位相同），继续作为结构性优化的首要证据。
