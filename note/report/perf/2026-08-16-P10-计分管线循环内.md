# P10 — 计分管线循环内（v0.4.48，结构性中性轮）

> 日期：2026-08-16 · 分支 `perf/plugin-performance`（第二期第 3 轮）
> 基线：v0.4.47（cbcf621）worktree 交替顺序交错 A/B · 红线：行为零变化（458 测试 + sinkΔ）

## 一、动机

P8 轮 JFR 归因中 playHand 引擎直连段仍有：ArrayList 快照（preSnap/jokersSnap/hookSnap/
activeJokers，~104B×3/手）、ArrayList$Itr（~32B×6-8/手）、HashMap$Node（handPlayedCount）。
本轮目标：快照池化 + 迭代器消除。

## 二、改动

1. **RunState 小丑快照深度分层池**：`jokerBufferPool[depth]`，acquire（clear+填充）/release
   严格配对。安全性论证：
   - **嵌套**：同时活跃的快照各占一层（实证用例：onPlayHand 钩子内再触发
     addCardToDeck→onCardAdded 分发、sellJoker→onAnySell），互不覆写；
   - **异常**：全部调用点 try/finally 释放，钩子抛异常不泄漏深度（与原「快照成垃圾」等价）；
   - **泄漏自愈**：漏调 release 只使下一层新建缓冲（有界增长，无正确性影响）；
   - **快照不出域**：12 处调用点均为即取即迭的局部循环，钩子签名不含快照列表，
     第三方无从持有；每层 acquire 时重建内容，语义与「每次新列表」逐字一致。
2. activeJokers 走同池空缓冲变体（playHand 计分区 try/finally 包裹）。
3. 热路径增强 for → 下标循环（playHand 选牌/held/玻璃/debuffHand/bones、discard、
   drawOne、effectBk/hasChicot、updateBellCard、endRound 金牌/蓝蜡封/租赁/永恒、
   RunState.sellJoker/destroyCard/addCardToDeck、Shop.reroll）。

### 为什么 playHand 分配逐字节持平（负结果分析）

JFR 对 cur 二进制复采样证实：playHand 场景中原有的 ArrayList/迭代器分配栈**已全部消失**
（改动确实生效），但 ThreadMXBean 总量不变。结论：**这些 32~104B 的短命小对象在 C2
稳态多已被逃逸分析标量消除**（此前 JFR 采样到的分配来自解释/C1 阶段）；池化真正兑现的
只有 EA 难以消除的段（roundCycle 的 startRound/endRound/弃牌分发路径，−1,139B/op 三对
一致）。教训入方法论：**JFR 分配归因须区分「稳态仍分配」与「仅预热期分配」——
以改动前后 ThreadMXBean 总量为准，JFR 只用于定位候选**。

### 方法学加固（本轮事故）

第一轮 A/B 数据作废：产物 jar 混入旧类（增量编译缓存损坏，新 RunState.class + 旧
Engine.class 并存），表现为 cur 与基线分配逐字节相同。由 `javap` 反汇编缺 playHand
方法暴露。**协议新增硬门**：每轮发版产物必须做符号校验（本轮标记字符串存在于对应
class），异常时 clean 重建；本轮复测即在 clean 重建+符号验证后进行。
另获得一组同二进制噪声标定：playHand 中位数 ±5%、discard 套件内可达 2×。
