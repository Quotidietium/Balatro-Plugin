# P9 — 商店生成层（v0.4.47）

> 日期：2026-08-16 · 分支 `perf/plugin-performance`（第二期第 2 轮）
> 基线：v0.4.46（96015a3）worktree 交替顺序交错 A/B · 红线：行为零变化（458 测试 + sinkΔ）

## 一、热点定位

P8 轮 JFR 采样中 Shop.genShop/makeJokerItem 归因 ~6%（135MB）；读码发现三重成本：

1. **CPU 主热点——makeJokerItem 的全量稀有度筛选**：每次生成小丑商品遍历 ORDERED
   150 个小丑，逐个 `JokerRegistry.rarityOf(key)`（String 哈希表查找）。商店每次生成
   2~4 商品（含重掷），多数为小丑（权重 70）→ 每次开店 ~6 次筛选 × 150 查找 ≈
   900 次字符串哈希查找；playHand 场景每 ~5 op 开一次店，成为其时间大头。
2. 池/权重表逐次重建：`List<int[]>` 权重（每次 4~5 个 int[] 装箱）、塔罗池（22 元素
   ArrayList+扩容链）、幻灵池、包池、券可用池每次现筛复制；标准局（无禁入）下塔罗池
   与 `Data.TAROTS` 内容序完全相同，纯冗余。
3. 空池回退 `List.of(Data.Tarot.values())` 每次新建（现共享 `Data.TAROTS`）。

## 二、改动（Shop.java）

| # | 改动 | 等价性论证 |
|---|---|---|
| 1 | `JOKERS_BY_RARITY` 静态分桶（4 桶 List.copyOf，桶内 ORDERED 序） | 原「遍历 ORDERED 保留 rarity 匹配项」的产出 = 桶本身（同元素同序）；后续 cavendish/noJokers/禁入/已持有过滤逐字保留 |
| 2 | 塔罗池无禁入直用 `Data.TAROTS`；幻灵池静态 `SHOP_SPECTRAL_POOL`（SPECTRALS−SPECIAL，同序）；包池静态 `SHOP_PACK_POOL`（PACKS−SPECTRAL，同序） | pick 的索引在「同内容同序」的池上映射到同一元素，随机流消耗不变 |
| 3 | 权重表平置 int 数组 + `weightedPick` 内联 | 与 `Rng.Stream.weighted` 逐位一致：total 按同序逐元素 int→double 累加；恰一次 `next()`；按序减重 `r<0` 即中；末元素兜底；空/全≤0→塔罗(1) |
| 4 | 列表预置（ShopData 4/2/2、items=shopSlots、avail=32） | 仅容量语义，内容不变 |

随机流红线：全部改动**零触碰**流名/调用次序/消耗次数（加权抽取与 pick 的 next() 次数
均与原实现相同，选取映射逐位等价）。

## 三、测量（best-of-3，交替顺序 A/B：cur→p8 / p8→cur / cur→p8）

| scenario | v0.4.46 ns/op | v0.4.47 ns/op | 加速比 | 分配 B/op |
|---|---:|---:|---:|---|
| shopGen | 12,501 | 3,645 | **3.430×** | 11,873 → **8,023**（−32.4%） |
| playHand | 8,630 | 5,386 | **1.602×** | 11,550 → **10,150**（−12.1%） |
| fullRun | 935,061 | 786,432 | **1.189×** | 2,000,677 → 1,991,963（−0.4%） |
| 几何平均（3 场景） | | | **1.869×** | |

三对原始中位数（两方向均一致）：shopGen 17,704/12,721/12,501 → 3,655/3,645/4,282；
playHand 8,810/8,630/8,675 → 5,416/5,395/5,386；fullRun min 803K/836K/840K →
845K/786K/711K。fullRun 的 +19% 为真实收益：每局 ~24 次开店 × 每次省 ~10μs ≈ 100μs/局，
与观测相符。

playHand 时间降幅（−37.6%）远大于分配降幅（−12.1%）——本轮主收益在 CPU 侧
（rarityOf 查找消灭），佐证热点定位 1。
