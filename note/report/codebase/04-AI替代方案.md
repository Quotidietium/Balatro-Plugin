# 04 — AI 工作流替代方案

> 代码基线 v0.4.60（2026-08-17）。
> **重要前提**：本项目运行时是**确定性游戏引擎**（种子复现红线、530 测试逐值断言），
> 运行时组件**不适用** AI 替代——AI 的替代面在**维护工作流**（开发/验证/发版环节），
> 而非插件本身。本报告按此口径评估。

## 1. 评估体系

六维评分（1-5，越高越利于 AI 化）：确定性 / 输入结构化 / 安全风险（出错影响小=高分）/
领域复杂度（通用=高分）/ 上下文窗口需求（局部=高分）/ 重复性。

| 等级 | 总分 | 策略 |
|---|---|---|
| 🤖 完全 AI 化 | 24-30 | AI 直接执行，产物抽检即可 |
| 🧑‍💻 AI 辅助 | 15-23 | AI 产初稿/建议，人工审核落地 |
| 👤 人工主导 | 6-14 | AI 仅提供参考 |

## 2. 逐项评估

### 2.1 版本发布说明撰写 — 🤖 完全 AI 化（26/30）

| 维度 | 分 | 依据 |
|---|---|---|
| 确定性 | 4 | 产出结构固定：基线/改动/兼容性/验证四要素（73 份既有 release 均循此） |
| 输入结构化 | 5 | git log（细粒度 commit）+ diff + 测试输出，全部机器可读 |
| 安全风险 | 5 | 纯文档，错误可被后续修订，无运行时影响 |
| 领域复杂度 | 3 | 需理解改动语义，但 commit message 已高密度承载 |
| 上下文需求 | 4 | 单版本增量，局部上下文足够 |
| 重复性 | 5 | 每版一次，73 次已发生 |

**现有基础**：commit message 极详尽（含轮次号/验证证据）；release 结构模板化。
→ Blueprint 见 [blueprints/01-release-note-writer.md](blueprints/01-release-note-writer.md)

### 2.2 文档一致性核对 — 🤖 完全 AI 化（24/30）

代码/golden/desc/help/README/基准文档六域核对（审计战役 #69-#75/#74 的产出面）。
确定性 4（对错可判）、输入 4、安全 5、领域 4、上下文 3、重复 4。
**现有基础**：表述-实现三向核对已是制度化镜头；部分面已有测试锁
（BossDescMultiplier/DescNameReference/HelpPagination/BenchScenarioDocConsistency），
AI 补测试锁覆盖不到的语义面。

### 2.3 REF 对照移植新内容 — 🧑‍💻 AI 辅助（20/30）

新小丑/消耗品/Boss 的 REF JS→Java 移植。确定性 4（逐方法翻译）、输入 5（REF 是
结构化源码）、安全 3（错移植会被黄金测试抓，但黄金本身要先重生成）、领域 2（需
钩子框架与流纪律知识）、上下文 3（需 Joker 接口+同类小丑范例）、重复 3（REF 更新
才触发）。
**关键依赖**：`tools/gen-golden.mjs` 重生成黄金 → 逐值断言兜底。人工审核点：流名
与调用顺序（种子复现红线）。
→ Blueprint 见 [blueprints/03-ref-porting-assistant.md](blueprints/03-ref-porting-assistant.md)

### 2.4 审计轮执行 — 🧑‍💻 AI 辅助（16/30）

按镜头库选题→读码→修复→变异验证的轮次。确定性 2（发现不可预知）、输入 4、
安全 3（误修风险，但有测试+commit 可回滚）、领域 2（需审计方法学内化）、上下文 2
（常需跨文件全域视角）、重复 4（224 轮已发生）。
**事实**：本项目 R1-R224 审计即由 AI agent 深度执行——本项评估是对既有实践的制度化
固化，非设想。人工介入点：轮次选题优先级、决策拍板（如 R165 开放决策点）、零缺陷
判定收官。
→ Blueprint 见 [blueprints/02-audit-round-executor.md](blueprints/02-audit-round-executor.md)

### 2.5 性能优化轮 — 🧑‍💻 AI 辅助（16/30）

识别热点→改动→best-of-3 交错 A/B→报告。确定性 3（协议固定但结果不可预知，含
负结果轮 P12）、输入 4（基准数据结构化）、安全 2（红线多：种子复现/API 契约/行为
零变化，靠 sinkΔ 逐位一致兜底）、领域 2（JVM 性能直觉+TLAB/JFR 知识）、上下文 2、
重复 3。
**已验证模式**：P1-P15 十五轮全部 AI 执行完成，方法论（协议/产物符号校验硬门/负
结果回退）已沉淀 note/性能优化.md。

### 2.6 实机验证（live-bot） — 🧑‍💻 AI 辅助（18/30）

check 场景脚本化执行+结果判读。确定性 3、输入 3（环境状态半结构化）、安全 4
（测试服沙箱）、领域 3（协议/环境坑多，9 条踩坑规约）、上下文 3、重复 3。
**已验证模式**：R220-R224 十七项清单即此方式完成。

### 2.7 运行时游戏逻辑 — 👤 不适用（结构性排除）

引擎/渲染/会话层为确定性代码，引入运行时 AI（LLM 调用）将破坏：种子复现红线、
530 测试的可断言性、单服 20 假人 TPS 20.0 的性能面、零外部依赖的部署简洁性。
**结论：运行时零 AI 化，这是本项目的正确设计。**

### 2.8 内容设计决策（新机制/对 REF 的偏离） — 👤 人工主导

6 处对 REF bug 的有意修正均需联网核实真版规则+用户拍板（note/release/逻辑审计.md）；
架构级决策（R165 类）同样。AI 仅提供候选与证据。

## 3. 函数级接口契约（AI 化候选的输入输出定义）

### 3.1 release-note-writer

| 项 | 契约 |
|---|---|
| 输入 | 上一版本 tag..HEAD 的 git log（细粒度）、`git diff --stat`、`./gradlew build` 测试输出、上一份 release note |
| 前置条件 | 版本号已在 build.gradle.kts:6 更新；构建绿 |
| 输出 | `note/release/<版本号>.md`：基线/改动（按 fix/test/docs 分组）/兼容性/验证四节 |
| 不变式 | 每条改动可追溯到一笔 commit；验证节只陈述实际执行过的验证（禁编造——全局红线） |
| 错误场景 | commit 语义不明 → 标注待确认而非猜测（用户全局规则：歧义须问） |

### 3.2 audit-round-executor

| 项 | 契约 |
|---|---|
| 输入 | 轮次选题（镜头名）、note/审计方法学.md、目标代码面 |
| 前置条件 | 工作树干净；全量测试绿 |
| 输出 | 发现清单（或零缺陷结论）+ 修复（若有，配变异验证的回归测试）+ 稳定性审计.md 轮次章 + 细粒度 commit |
| 不变式 | 新守门测试必须变异验证；修复必须全量测试过；决策点呈报用户不自行拍板 |
| 错误场景 | 嫌疑否证 → 记录否证过程（R115/R117 式），不算失败轮 |

### 3.3 ref-porting-assistant

| 项 | 契约 |
|---|---|
| 输入 | REF/balatro/js 新增/变更的 defJoker/消耗品定义 |
| 前置条件 | JokerRegistry.register 可用（运行期注册 API，JokerRegistry.java:50-52）；jokermeta.txt 需同步 |
| 输出 | BasicJoker 枚举新常量（钩子覆写）+ jokermeta 条目 + 重生成 golden + 单测 |
| 不变式 | 流名与调用顺序与 REF 逐字一致（RngStreamInventoryTest 会抓）；钩子集合 0 缺失 0 多余 |
| 人工审核点 | 流序、desc 文案、与真版规则的偏差判定 |

## 4. ROI 矩阵与路线图

```
高收益 + 低难度 → 🥇 立即：release-note-writer（26 分，每版必用）
高收益 + 高难度 → 🥈 规划：audit-round-executor（制度化已验证的实践）
低收益 + 低难度 → 🥉 逐步：docs-consistency（补测试锁外语义面）
低收益 + 高难度 → 📋 搁置：运行时 AI（结构性排除，永不）
```

**路线图**：

- Phase 1（即时）：固化 release-note-writer 为 skill——输入零增量（commit log 已够
  详细），收益立现（每版 30-60 分钟人工撰写时间）。
- Phase 2（近期）：audit-round-executor 与 ref-porting-assistant 固化为 skill；两者
  共享「全量测试+变异验证+细粒度 commit」的后置约束。
- Phase 3（按需）：性能轮与实机轮暂不固化——note/性能优化.md 与 tools/live-bot/
  README 的协议文档已足够作为每次执行的操作手册。

## 5. 结论

本项目的独特之处在于：**它已经是 AI 深度参与维护的项目**（224 轮审计、15 轮性能
战役、实机验证均由 AI agent 按 note 中的制度执行）。因此 AI 替代方案的重点不是
「引入 AI」，而是把已被证明的工作流（发布说明、审计轮、移植）固化为可复用的
Skill 规格（见 blueprints/），把隐性实践变成显性契约。运行时保持零 AI——这与
引擎的确定性红线一致，是设计而非局限。
